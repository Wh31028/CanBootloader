| 문제 | 해결 | 기억할 이유 |
| --- | --- | --- |

## 꼭 알아야 할 개념

### 1. Flash padding과 CRC

- 이 F103 driver는 4 byte 단위로 Flash를 쓴다.
- firmware 끝이 1~3 byte 남으면 `0xFF`를 붙여 4 byte로 쓴다.
- CRC에는 붙인 `0xFF`를 넣지 않는다. BBB가 계산한 원본 firmware CRC와 같아야 하기 때문이다.

### 2. Cortex-M vector table

application 시작 주소 `0x08004000`의 처음 8 byte는 다음 두 값이다.

| 위치 | 값 | 정상 조건 |
| --- | --- | --- |
| 첫 4 byte | Initial MSP | SRAM `0x20000000`~`0x20005000` 안, 4-byte aligned |
| 다음 4 byte | Reset Handler | bit 0 = 1(Thumb), 실제 주소는 active application range 안 |

`0x20005000`은 SRAM 끝 주소이지만, 첫 push 전의 stack top이므로 Initial MSP로 허용한다.

### 3. CRC와 vector 검사의 차이

- CRC: 받은 byte가 보낸 byte와 같은지 확인
- vector 검사: 그 byte를 application으로 실행해도 되는지 확인

둘 다 통과해야 한다.

## 설계 선택

| 선택 | 장점 | 하지 않은 것 |
| --- | --- | --- |
| vector를 마지막에 write | copy 도중 reset되어 새 image를 완성본으로 오인할 가능성을 낮춤 | true A/B update 구현 |
| staging을 먼저 검증 | invalid image 때문에 기존 active app을 erase하지 않음 | metadata page 구조 변경 |
| copy 뒤 active CRC를 다시 계산 | write/readback 문제를 발견 | write API 성공만으로 완료 처리 |

이 방식은 true A/B나 atomic update가 아니다. 하나의 Flash 안에서 staging 후 copy하는 구조이며, power-loss metadata transaction과 rollback은 F3 범위다.

## 30초 답변

### Q1. Flash erase 단위와 program alignment가 copy 설계에 미치는 영향은 무엇인가?

- 상태: `DRAFT`
- 답변: F103은 page 단위로 erase하지만 이 driver는 4 byte 단위로 program합니다. 그래서 firmware 길이가 4의 배수가 아니면 기존 copy의 마지막 write가 실패할 수 있었습니다. 이번에는 남는 1~3 byte를 `0xFF`로 채워 4 byte write로 만들었습니다. CRC는 padding을 빼고 원본 길이만 계산해서 BBB가 보낸 CRC와 호환됩니다. Flash 주소 범위도 덧셈 overflow가 나지 않는 subtraction 방식으로 검사했습니다.

### Q2. Initial MSP, Reset Handler, Thumb bit를 왜 검증해야 하는가?

- 상태: `DRAFT`
- 답변: CRC가 맞아도 그 데이터가 STM32 application이라는 뜻은 아닙니다. MSP가 SRAM 밖이면 stack을 제대로 쓸 수 없고, Reset Handler의 bit 0이 0이면 Cortex-M Thumb 실행 조건을 만족하지 않습니다. 또 handler가 staging을 가리키면 임시 데이터를 실행할 수 있습니다. 그래서 normal boot, recovery, CAN JUMP가 같은 helper로 MSP, Thumb bit, active range를 검사하게 했습니다.

### Q3. Vector-last copy는 true A/B나 atomic update와 어떻게 다른가?

- 상태: `DRAFT`
- 답변: vector-last는 application을 시작하게 하는 첫 8 byte를 마지막에 쓰는 방법입니다. copy 중 reset이 나도 새 image가 완성된 것처럼 jump할 가능성을 줄입니다. 하지만 독립된 두 Flash slot이나 atomic slot swap, 이전 version rollback은 제공하지 않습니다. 따라서 true A/B update가 아니라 single-Flash staging/copy의 안전성 보강입니다.

## 2분 답변

### Q. CRC와 vector 검증을 함께 둔 이유와 실제 구현을 설명해보세요.

기존 bootloader는 staging CRC가 맞으면 active 영역을 erase하고 copy했습니다. 하지만 metadata write 실패를 확인하지 않았고, copy 마지막 길이가 4 byte의 배수가 아니면 Flash write가 실패할 수 있었습니다. 또 boot 여부는 Reset Handler가 넓은 Flash 범위 안에 있는지만 봤습니다. CRC가 맞는 random data도 application처럼 보일 여지가 있었습니다.

수정 후에는 먼저 staging image의 vector table을 검사합니다. MSP가 F103RB SRAM 안에 있는지, Reset Handler가 Thumb인지, 그 주소가 active application 영역을 가리키는지 확인합니다. 그 다음 metadata size와 CRC를 모두 write할 수 있을 때만 active erase를 시작합니다. firmware 끝은 `0xFF` padding으로 4 byte write를 맞추고, 실행 시작 정보인 첫 8 byte는 마지막에 기록합니다. 마지막으로 active 영역의 원본 길이 CRC와 vector table을 다시 확인합니다. normal boot, recovery, CAN JUMP도 같은 `bootVerifyFw()`를 사용합니다.

실제로 F103 bootloader와 application은 cross-build에 성공했고 application vector 값도 확인했습니다. 하지만 BBB/STM32F103RB 연결 시험은 이 세션에서 실행하지 못했으므로 `NOT RUN`입니다. 이 설계는 true A/B가 아니며, 실제 power-loss recovery와 transactional metadata는 F3에서 다룰 내용입니다.
