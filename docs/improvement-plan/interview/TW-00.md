## 반드시 이해할 기반 지식

### F103 memory map과 boot flow

- 정의: bootloader vector table은 `0x08000000`, active application vector table은 `0x08004000`이며, current Custom staging payload는 `0x08012000`부터다.
- 이 프로젝트에서 필요한 이유: bootloader는 active image의 first 8 B(SP와 Reset Handler)를 마지막에 copy해 reset 중 invalid image jump 위험을 낮춘다.
- 현재 구현과의 연결: `boot_can_custom_f103/App/hw/hw_def.h`와 `boot_can_fw_f103/STM32F103XX_FLASH.ld`가 57,336 B (`0xDFF8`) application/staging limit를 정한다.
- 흔한 오해: staging 후 copy는 STM32의 physical dual-bank/A/B update나 atomic slot swap이 아니다.

### Build provenance와 baseline

- 정의: 동일 source commit, compiler, build command, artifact hash/size를 함께 보존해야 이후 binary-size 또는 build-result 차이를 해석할 수 있다.
- 이 프로젝트에서 필요한 이유: `docs/f103-fota-baseline.md`의 과거 binary size는 FreeRTOS 추가 전 기록이므로 current build size의 대체값이 아니다.
- 현재 구현과의 연결: 실제 clean build에서 Custom bootloader 9,832 B, application 10,180 B가 생성됐고 ISO-TP는 compile FAIL이었다.
- 흔한 오해: build가 성공했다는 사실은 hardware FOTA 성공이나 protocol fault handling 검증을 뜻하지 않는다.

### CAN transport와 application protocol의 경계

- 정의: Classic CAN controller의 frame CRC/automatic retransmission과 application의 DATA omission, ACK/NACK retry는 다른 층의 사건이다.
- 이 프로젝트에서 필요한 이유: Custom protocol은 sequence bitmap NACK으로 missing DATA를 선택 재전송하지만 ACK loss를 식별할 block/session ID는 없다.
- 현재 구현과의 연결: `custom_fota.c:start_custom_fota()`와 target `bootProcessData()`의 ACK-loss desynchronization은 source review로 확인했다.
- 흔한 오해: SocketCAN send count는 physical bus의 automatic retransmission on-wire count가 아니다.

## 30초 답변

### Q1. 전체 FOTA 경로와 각 component의 책임은 무엇인가?

- 상태: `DRAFT`
- 답변: BBB dashboard나 CLI가 C flasher를 실행하고, flasher가 SocketCAN으로 FOTA entry `0x200#DEAD`와 Custom command `0x100`을 보냅니다. F103 application은 backup register magic을 남기고 reset해 bootloader로 넘깁니다. bootloader는 firmware를 `0x08012000` staging에 받고 CRC32를 확인한 뒤 active application `0x08004000`으로 copy합니다. 완료 전까지 active image는 건드리지 않는 것이 staging의 책임입니다. 이 경로는 `docs/architecture.md`와 TW-00 clean Custom build로 기준을 고정했지만, 이번 Task에서는 hardware 전송을 실행하지 않아 end-to-end는 NOT RUN입니다.

### Q2. 현재 target이 F407이 아니라 F103이라고 판단한 근거는 무엇인가?

- 상태: `DRAFT`
- 답변: 세 F103 target project의 CMake source가 `STM32F103xB`, `startup_stm32f103xb.s`, `system_stm32f1xx.c`를 선택하고, linker가 Custom bootloader 16 KiB와 application `0x08004000` origin을 설정합니다. 실제 Arm GNU Toolchain clean build도 Cortex-M3 설정으로 Custom bootloader와 application에서 PASS했습니다. 따라서 F407 실험 source가 있어도 current baseline target은 STM32F103RB입니다.

### Q3. 과거 direct-write benchmark와 현재 staging 구조를 왜 분리해야 하는가?

- 상태: `DRAFT`
- 답변: 과거 64 KiB direct-write는 active image에 바로 쓰는 구조이고, current Custom은 57,336 B 한도에서 staging 수신 후 CRC 검증과 active copy를 수행합니다. 시간에는 image size, erase/write backend, copy 비용이 모두 영향을 줍니다. 따라서 두 결과를 protocol throughput 차이라고 비교하면 bias가 생깁니다. 이번 baseline은 current source commit, toolchain, BIN hash/size를 별도로 기록했습니다.

## 2분 답변

### Q. 이번 baseline을 어떻게 신뢰할 수 있게 만들었는가?

TW-00의 목적은 기능을 고치는 것이 아니라 이후 변경의 비교 계약을 고정하는 것이었습니다. 먼저 실제 source에서 F103 identity를 확인했습니다. 세 프로젝트는 `STM32F103xB`, F103 startup/system source를 쓰며, current Custom map은 bootloader 16 KiB, application과 staging payload가 각각 57,336 B입니다. 그다음 repository build directory를 재사용하지 않고 temporary directory에서 Arm GNU Toolchain 15.2.1로 clean build했습니다. Custom bootloader는 9,832 B, FreeRTOS application은 10,180 B로 PASS했고 hash도 남겼습니다. ISO-TP는 `isotp_port.h` include order 때문에 `uint8_t` 등 type 오류로 FAIL했으므로, 성공한 것처럼 기록하지 않고 TW-04 defect로 남겼습니다.

성능 해석에서도 현재 staging 구조를 과거 64 KiB direct-write benchmark와 분리했습니다. staging은 CRC 검증 전 active image를 보존하고 copy recovery를 돕지만 true dual-bank/A-B나 atomic rollback은 아닙니다. 실제 hardware와 BBB/Linux flasher build는 이 macOS 세션에서 실행하지 못했으므로 NOT RUN입니다. 또한 physical bit/CRC fault와 precise on-wire retransmission 수는 장비 제약상 범위 밖입니다. 이렇게 source fact, build artifact, 실행 여부와 limitation을 분리해야 다음 안전성 Task의 결과를 과장하지 않고 비교할 수 있습니다.

## 예상 꼬리질문

### 왜 staging을 true A/B라고 부르지 않는가?

답변: F103 internal Flash 한 개를 active와 staging으로 나눈 뒤 staging에서 active로 copy할 뿐, 독립 slot boot selection이나 atomic bank swap이 없다. staging corruption이면 이전 active image를 자동 rollback하는 것도 보장하지 않는다.

### ISO-TP build failure를 왜 바로 고치지 않았는가?

답변: Task 목적이 defect repair가 아니라 변경 전 baseline 고정이기 때문이다. 수정하면 baseline과 TW-04 결과가 섞인다. 현재 compile command와 direct cause를 report에 남겨 TW-04에서 재현 test로 사용한다.

### 이번 결과로 CAN 신뢰성을 주장할 수 있는가?

답변: 아니다. compile evidence와 source review만 있다. BBB/Linux flasher build와 F103/BBB CAN hardware transfer는 NOT RUN이다. physical bit/CRC fault 및 automatic retransmission의 on-wire 횟수 정밀 계측도 범위 밖이다.
