## 이번 Task를 한 문장으로 설명

Custom CAN FOTA의 wire format은 유지하면서 target bootloader가 invalid START를 erase 전에 거부하고, state·DLC·sequence·누적 byte precondition을 만족하는 DATA/END/JUMP만 처리하도록 만들어 malformed frame이 staging erase, CRC/copy 또는 application jump로 이어지지 않게 했다.

## 실제 문제와 코드 근거

| 문제 | File/function | 위험 |
| --- | --- | --- |
| invalid size가 local 변수만 clamp됨 | `boot_can.c:bootProcessStart()` (변경 전) | `original_fw_size`가 0/oversize로 남아 erase/CRC 및 subtraction 경계가 깨짐 |
| command 순서 guard 부재 | `boot_can.c:bootProcess()` (변경 전) | IDLE DATA/END/JUMP가 flash/copy/jump path에 진입 가능 |

| END complete-image 확인 부재 | `boot_can.c:bootProcessEnd()` (변경 전) | 모든 logical byte가 commit되기 전 CRC/copy 시도 가능 |

## 반드시 이해할 기반 지식

### Finite state machine과 precondition

- 정의: state와 event별로 허용 전이만 정의해, event 자체가 아니라 현재 phase와 함께 해석하는 방식이다.
- 이 프로젝트에서 필요한 이유: CAN command byte만으로는 START 이전 DATA와 정상 DATA를 구분할 수 없다. `IDLE → RECEIVING → IMAGE_VERIFIED`라는 local context가 있어야 flash side effect 전에 거부할 수 있다.
- 현재 구현과의 연결: `boot_state`와 `bootProcessStart/Data/End/Jump()` guard가 `ERR(0x07)` 또는 input ERR을 반환한다.
- 흔한 오해: state machine이 session ID를 대체하지 않는다. v1에는 block/session identity가 없어 ACK loss 뒤 stale frame은 F1에서 해결해야 한다.

### DLC, sequence, logical byte length

- 정의: Classic CAN DLC는 frame의 실제 payload byte 수이며, Custom DATA는 byte 0 header와 최대 7-byte firmware payload를 갖는다.
- 이 프로젝트에서 필요한 이유: 256-byte block은 37 frame이고 full block의 seq 36 payload는 4 bytes다. 마지막 logical block은 `ceil(block_len/7)`까지만 허용되며 마지막 frame의 DLC도 달라진다.
- 현재 구현과의 연결: `block_expected_bytes`를 `original_fw_size - total_received_bytes` 이후에만 계산하고 `seq < expected_frames_in_block`, `msg->dlc == expected_payload_len + 1`을 확인한다.
- 흔한 오해: CAN DLC 8이라고 항상 firmware 8 bytes가 아니다. header 1 byte를 제외하면 최대 7 bytes다.

### duplicate와 out-of-order의 범위

- 정의: 같은 미완료 block의 이미 수신된 sequence는 duplicate이고, 아직 안 받은 유효 sequence는 out-of-order이지만 bitmap으로 허용된다.
- 이 프로젝트에서 필요한 이유: bitmap NACK 방식은 sequence 순서가 아닌 complete bitmap을 기준으로 block을 commit한다.
- 현재 구현과의 연결: duplicate bit는 overwrite하지 않고, valid unseen sequence만 copy 후 mark한다. last sequence duplicate는 NACK을 재전송한다.
- 흔한 오해: 이것이 ACK loss 뒤의 이전 block frame까지 안전하게 구별한다는 뜻은 아니다. wire에 block ID가 없어서 그 경우는 Protocol v2 과제다.

## 설계 결정과 trade-off

| 결정 | 선택 이유 | 대안 | 선택하지 않은 이유 |
| --- | --- | --- | --- |
| target local state 추가 | wire compatibility를 유지하며 side effect 이전에 command order를 차단 | session ID/block ID 추가 | packet layout과 BBB/Yocto sender를 함께 바꾸는 Protocol v2 범위 |
| exact DLC와 reserved control sequence 검사 | length를 deterministic하게 만들어 bitmap/offset 오염 차단 | `>=` DLC 허용 및 payload truncate | malformed frame을 정상 data로 오인할 수 있음 |
| duplicate no-overwrite | 같은 block의 retransmission이 이미 안전히 받은 RAM data를 바꾸지 않음 | duplicate payload 재복사 | data 값이 다른 duplicate도 silent overwrite될 수 있음 |
| JUMP는 `IMAGE_VERIFIED`만 허용 | FOTA mode에서 START 없는 application 전이를 막음 | valid existing app이면 IDLE JUMP 허용 | update abort와 jump의 별도 정책이 없고, 이번 Task는 최소 안전 전이를 우선 |

## 실패 시나리오를 순서대로 설명

```text
1. 기존에는 IDLE에서 DATA 또는 END가 들어와도 dispatch되었다.
2. DATA는 original_fw_size=0에서 unsigned subtraction을 수행할 수 있고, END는 staging CRC/copy path로 갈 수 있었다.
3. 수정 후 IDLE의 DATA/END/JUMP는 flash access 전에 ERR(0x07)로 종료한다.
4. valid START만 erase 후 RECEIVING으로 바꾸며, malformed START는 기존 context/staging을 건드리지 않는다.
5. RECEIVING에서도 exact seq/DLC가 맞고 모든 logical byte가 block write된 뒤에만 END CRC/copy를 허용한다.
```

## 30초 답변

### Q1. Bootloader protocol에 명시적 state machine이 필요한 이유는 무엇인가?

- 상태: `DRAFT`
- 답변: CAN header만 보면 DATA인지 END인지는 알 수 있지만 그것이 어떤 update phase의 command인지는 알 수 없습니다. 기존 bootloader는 START 없이도 DATA/END/JUMP를 dispatch해 unsigned byte count 계산이나 CRC/copy path로 갈 수 있었습니다. 그래서 wire format은 바꾸지 않고 target에 `IDLE`, `RECEIVING`, `IMAGE_VERIFIED`, `FAILED` state를 두었습니다. 이제 DATA/END/JUMP는 허용 state가 아니면 flash 접근 전에 `ERR(0x07)`로 끝납니다. 다만 session/block ID는 없어서 ACK loss 뒤 stale frame은 Protocol v2의 별도 문제입니다.

### Q2. Invalid size와 잘못된 DLC가 어떤 flash 위험으로 이어질 수 있는가?

- 상태: `DRAFT`
- 답변: 이전 START는 size 0이나 57,336 B 초과도 staging erase를 수행하고 original size에는 invalid 값을 보존했습니다. DATA에서는 그 값과 received byte를 빼므로 underflow 또는 잘못된 CRC 범위의 원인이 됩니다. 또 DLC가 짧으면 기대하지 않은 payload를 bitmap 완료로 처리할 수 있습니다. 수정 후 START는 정확히 DLC 5와 `1..57,336`을 erase 전에 검사하고, DATA는 block별 expected sequence와 `1 + payload length` DLC를 모두 검사합니다. invalid input은 bitmap이나 flash를 바꾸지 않습니다.

### Q3. Duplicate와 out-of-order DATA를 어떤 정책으로 처리했는가?

- 상태: `DRAFT`
- 답변: 같은 미완료 block 안에서는 bitmap이 아직 0인 유효 sequence를 out-of-order로 받아들이고, 이미 1인 sequence는 duplicate로 보고 RAM buffer를 overwrite하지 않습니다. 마지막 sequence duplicate는 host가 다시 feedback을 받을 수 있게 current NACK bitmap을 보냅니다. 이 선택은 Selective NACK의 frame reorder tolerance는 보존하지만, block ID가 없으므로 commit ACK 유실 뒤 이전 block duplicate를 구분하지 못합니다. 그 session-level idempotency는 F1 Protocol v2에서 다룹니다.

## 2분 답변

### Q. malformed CAN frame이 flash erase로 이어지지 않게 어떻게 막았는가?

기존 F103 Custom bootloader는 START의 size를 local variable만 clamp하고 original size에는 invalid 값을 남긴 채 staging 56 KiB를 erase했습니다. 그리고 command order state가 없어서 START 이전 DATA나 END도 해당 handler에 들어갈 수 있었습니다. 이 구조에서는 malformed input이 flash side effect나 unsigned length 계산으로 이어질 수 있었습니다.

이번에는 CAN ID와 header layout을 바꾸지 않았습니다. BBB sender가 보내는 정상 START/END DLC 5, JUMP DLC 1, DATA 최대 7-byte payload라는 v1 contract는 유지했습니다. 대신 target 내부에 local state를 추가해 valid START가 성공한 뒤에만 `RECEIVING`으로 전이하게 했습니다. START는 DLC 5, header sequence 0, size `1..57,336`을 먼저 통과해야 erase를 호출합니다. DATA는 남은 logical byte를 먼저 안전하게 계산하고 현재 block의 expected sequence와 exact DLC를 검사한 뒤에만 memcpy와 bitmap mark를 합니다. END는 `total_received_bytes == original_fw_size`이고 incomplete bitmap이 없을 때만 CRC/copy를 시작하며, JUMP는 `IMAGE_VERIFIED`에서만 허용됩니다.

cross-build는 Arm GNU 15.2.1으로 실제 실행해 PASS했고 F103 image는 Flash 10,068 B, RAM 3,184 B였습니다. 이어 BBB `can0` 500 kbit/s와 STM32F103RB에서 negative command 10개와 normal Custom FOTA를 실제 실행했다. 모든 새 ERR code와 normal ACK 흐름을 `candump -L` trace로 확인했고 JUMP 뒤 application도 정상 복귀했다. flash/RAM을 ST-LINK로 별도 dump하지는 않았으므로 side effect는 hardware response와 early-return code path를 함께 근거로 기록했다. 물리 bit/CRC fault 주입과 on-wire automatic retransmission 정밀 계측은 이 Task 범위 밖입니다. ACK 유실 뒤 stale block frame을 해결하려면 wire-level block/session ID가 필요하므로 이번 local state 변경으로 과장하지 않고 F1로 남겼습니다.

## 예상 꼬리질문

### 왜 다른 방법을 쓰지 않았는가?

답변: session ID와 block ID를 넣으면 ACK loss와 stale frame까지 해결할 수 있지만 packet layout과 BBB/Yocto sender 호환을 바꾸는 Protocol v2다. TW-01은 existing v1 안전성 보강 범위라 local state와 validation만 추가했다.

### 이 설계도 실패할 수 있는 조건은 무엇인가?

답변: block commit ACK가 유실된 뒤 host가 이전 block의 last DATA를 재전송하면 target은 다음 block의 same sequence로 해석할 수 있다. 또한 metadata write result와 active copy validation은 아직 TW-02에서 강화해야 한다.

### 제품 수준으로 가려면 무엇이 더 필요한가?

답변: session/block identity와 idempotent response, bounded BBB retry/deadline, metadata transaction/recovery, vector/SP/CRC validation, image signature와 anti-rollback이 필요하다.
