# P03 — F407 hardware smoke와 측정 대조

## 처음 읽는 사람을 위한 실행 기록

이 절이 현재 상태의 기준이다. 이 아래에 남은 초기 계획은 당시의 사전점검 snapshot으로 보존한 것이며, 그 안의 `NOT RUN`과 허가 대기 문구는 이 절의 실제 실행 결과로 대체됐다.

### 결론

P03은 **IN_PROGRESS**다. F407 Custom protocol로 65,536 B application을 FOTA 한 번 전송했고, sender의 END CRC ACK와 target flash의 byte-for-byte readback 일치를 확인했다. ISO-TP hardware smoke, 양 방식 5회 반복, hardware omission/timeout, application 실제 boot 관측은 아직 하지 않았다. 따라서 P04 240회 본 실험은 시작하면 안 된다.

### 장비·주소·허가

| 구분 | 실제 확인값 |
| --- | --- |
| Target | STM32F4DISCOVERY, Device ID `0x413`, 1 MiB flash |
| ST-LINK | SN `066BFF3332584B3043252734`, V2J46M31, SWD 4 MHz |
| BBB | `debian@192.168.7.2`, beaglebone, Linux 4.19.94-ti-r42 |
| CAN | external transceiver, PD0=RX/PD1=TX(AF9), 종단 저항, `can0` 500,000 bit/s |
| Bootloader | `0x08000000`; 사용자에게서 exact Custom hashes에 대해 sector 0--2 erase/program/verify 허가를 받음 |
| Application | FOTA `[0x08010000, 0x08020000)`, 65,536 B; START가 sector 4만 erase |

Custom bootloader를 ST-LINK로 기록할 때 사용한 형식은 다음과 같다. `-e [0 2]`만 사용했으며 mass erase와 ST-LINK application write는 하지 않았다.

```powershell
STM32_Programmer_CLI -c port=SWD sn=066BFF3332584B3043252734 mode=UR reset=HWrst freq=4000 `
  -e [0 2] --skipErase -w <custom.bin> 0x08000000 -v
```

### build와 고정 artifact

CubeMX 설정은 F407 세 project에서 PCLK1=42 MHz, CAN prescaler 6, BS1=11 TQ, BS2=2 TQ, SJW=1 TQ로 하여 500 kbit/s가 되게 했다. build 검증은 `cmake --build boot_can_custom/build/Release --parallel`과 `cmake --build boot_can_isotp/build/Release --parallel`이며 둘 다 PASS다.

- 최종 Custom: `experiments/ksma-2026/p03-f407-500k-custom-tailfix-20261007/boot_can_custom-500k-stdid-tailfix.bin`, 33,488 B, SHA-256 `280410bf713630b66f16f233989486de60387a648cfa9b1ae6b1a201826e9391`.
- Application: `boot_can_fw-65536-ff.bin`, 65,536 B, SHA-256 `1badd29c53120916c2f2b0f2e773c6af953960bedeb1c199b66021096b9870e1`.
- ISO-TP candidate: 35,240 B, SHA-256 `7f9412a488186b0567c2c57a377fb9a8256cbc2aff4aafb45a343dcd647ae5eb`; build만 했고 flash하지 않았다.

### 발견한 실패와 수정

| run | 결과 | 원인/조치 |
| --- | --- | --- |
| smoke-01/02 | `FAIL_START` | 배선 미연결, `ERROR-PASSIVE`; 기록 보존 |
| smoke-03 | `FAIL_START` | target이 numeric `0x101`을 extended frame으로 응답. `canMsgWrite()`를 11-bit ID는 standard CAN으로 수정 |
| smoke-04 | `FAIL_END_CRC` | F407 readback의 첫 차이가 `0xfc`: 매 256-byte block 마지막 4 bytes가 `FF`로 남음. padded DLC=8 마지막 frame에서 남은 bytes만 복사하도록 clamp 수정 |
| smoke-05 | **`OK`** | standard ID와 tail fix 적용 뒤 CRC ACK·JUMP ACK 및 readback exact match |

ID type 변경은 P01 contract(Custom response standard `0x101`, ISO-TP response standard `0x7e8`)를 맞춘 wire-format 호환 수정이다. extended-only legacy client에는 영향이 있을 수 있다. tail fix는 offset 252의 마지막 frame을 256-byte buffer 안의 네 bytes로 잘라 복사하는 안전 경계 수정이다.

### 성공한 smoke-05 재현과 판정

BBB에서 bootloader LED 상태를 확인한 뒤 다음 sender를 실행했다. `candump`도 같은 run directory에 background capture했다.

```bash
python3 loss_test_custom.py \
  --firmware boot_can_fw-65536-ff-correct.bin \
  --run-dir custom-smoke-05 \
  --attempt-id p03-custom-500k-smoke-05 \
  --loss 0 --seed 2026100703 \
  --transaction-timeout 120 --can-interface can0
```

결과는 `transaction_status=OK`, monotonic `elapsed_sec=8.873758`, attempts/socket success `9474/9474`, drops/send errors/retransmit `0/0/0`, valid protocol RX 258, invalid RX 0이다. trace의 끝은 END CRC `100#804BD1B986` → `101#0000`, JUMP `100#C0` → `101#0000`이다. 최종 can0은 ERROR-ACTIVE, tx/rx error 0/0이었다.

시간은 START 직전부터 유효 END ACK 직후까지다. JUMP와 실제 boot는 시간에 포함되지 않으며 `boot_status=JUMP_SENT_NOT_VERIFIED`이므로 application 정상 기동은 아직 주장하지 않는다. BBB clock은 2026-08-10이고 unsynchronized였으므로 raw CSV의 UTC timestamp는 신뢰하지 않고 monotonic elapsed만 쓴다.

### F407 flash readback

성공 직후 아래 read-only 명령으로 application 64 KiB를 추출했다. 이 명령은 target에 쓰지 않는다.

```powershell
STM32_Programmer_CLI -c port=SWD sn=066BFF3332584B3043252734 mode=UR reset=HWrst freq=4000 `
  -r 0x08010000 0x10000 docs/paper-plan/reports/artifacts/P03-20261007/f407-app-after-custom-smoke-05.bin
```

dump는 65,536 B, SHA-256 `1badd29c53120916c2f2b0f2e773c6af953960bedeb1c199b66021096b9870e1`, first difference `-1`로 source application과 완전히 일치했다. 따라서 smoke-05는 END CRC ACK와 physical direct-write 내용 대조를 모두 통과했다.

## 초기 사전점검 근거 (보존용)

시작 시 worktree는 `paper/ksma-2026`이고 HEAD는 `26cd5c7699257baae51cbb6b94d9d9299528b1c4`였다. 두 ISO-TP submodule은 모두 `5593428d95af10dde1e565cebcda16089fc74857`였다. `git status --short --branch`에는 미커밋 파일이 표시되지 않았고, branch는 `origin/paper/ksma-2026`보다 1 commit ahead였다. `git diff --check` 및 untracked-file 조회도 출력이 없었다.

P00~P02 evidence와 예비 CSV는 읽기만 했고 수정하지 않았다. 다음 hardware 준비를 실제로 확인했다.

- target: `STM32F4DISCOVERY`, ST-LINK SN `066BFF3332584B3043252734`, firmware `V2J46M31`; 사용자 확인상 ST-LINK 복구 가능
- BBB: USB SSH `debian@192.168.7.2`, hostname `beaglebone`, Linux `4.19.94-ti-r42`
- `can0`: `UP`, `LOWER_UP`, `ERROR-ACTIVE`, 500,000 bit/s, sample point 0.875, error counter tx/rx 0/0
- `candump`: `/usr/bin/candump` 확인; sender 미실행 상태의 `timeout 10s candump -L can0`은 frame/오류 없이 종료
- F407 CAN1은 두 bootloader 모두 PD0=RX, PD1=TX(AF9)이고 사용자는 외부 transceiver 배선·종단이 이에 맞는다고 확인했다.

P00의 1 Mbit/s archive는 시험 binary로 사용하지 않는다. CubeMX 설정을 Custom/ISO-TP/application 모두 500 kbit/s (`PCLK1=42 MHz`, prescaler 6, BS1=11 TQ, BS2=2 TQ, SJW=1 TQ)로 변경했다. ISO-TP bootloader의 강제 `-O0`은 Custom과 같은 `-Os`, function/data section 및 `--gc-sections` 정책으로 맞췄다. 새 artifact는 아래와 같으며 아직 플래싱 대상으로 허가받지 않았다.

| 용도 | archive binary SHA-256 | program 주소 | 상태 |
| --- | --- | --- | --- |
| Custom bootloader (33,472 B) | `66cb0d40d77fe975237d87d3c95e298a9b3bd63bb987bae34c9aa5609887932a` | `0x08000000` | 미승인 |
| ISO-TP bootloader (35,224 B) | `d63862926aa56761ae0f8d8087b06f73cc2b7ffe381ad260b5f8b29c5de9cf80` | `0x08000000` | 미승인 |
| application 원본 (36,832 B) | `9a63c0b22eed4c95e0b4807bdc664822b0c91cbf3b9d91cdb7618d014e159346` | `0x08010000` | 전송하지 않음 |
| application 0xFF padded (65,536 B) | `1badd29c53120916c2f2b0f2e773c6af953960bedeb1c199b66021096b9870e1` | FOTA `[0x08010000, 0x08020000)` | 미승인 |

정상 비교에 필요한 F407 application 전송 범위는 `[0x08010000, 0x08020000)`이며 erase 범위는 sector 4 하나다. 새 application은 원본 bin에서 `0xFF` padding으로 65,536 B를 만들고 마지막 byte `0xFF`를 확인했다. ELF 절대주소를 `objcopy --pad-to 0x08020000`에 사용한 첫 시도는 402,588,280 B 잘못된 파일을 만들었으므로 archive에 보존했으며 Flash에는 사용하지 않는다. 올바른 파일은 원본 bin을 입력으로 `--pad-to 0x10000`을 사용해 별도 생성했다.

## 당시 Flash 실행 대기 사유 (실행 전 기록, 보존용)

대상·복구·BBB/CAN 구성은 확인됐지만, 위 exact hash에 대해 ST-LINK가 bootloader 영역만 program/verify하고 (mass erase 금지), 각 방식에서 64 KiB padded application을 FOTA로 sector 4에 기록하도록 하는 최종 명시 허가는 아직 받지 않았다. 그 전에는 Flash나 sender를 실행하지 않는다.

CubeIDE의 Windows 재생성으로 CMSIS/IDE metadata를 포함한 다수 파일의 줄바꿈/경로 노이즈가 생겼다. 사용자 승인 후 세 F407 프로젝트를 HEAD로 복원하고 위의 500 kbit/s 및 ISO-TP 최적화 변경만 재적용했다. 복원 전 의미 있는 diff는 `artifacts/P03-20261007/cubeide-before-cleanup-semantic.diff` (SHA-256 `309a792c5b217c6a98ae42dfd11954c0808dec6af8a1b5049d7f6f43f8d2d19b`)에 보존했다. 정리된 source 재build의 세 bin hash는 archive와 일치한다.
