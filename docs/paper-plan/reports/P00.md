변경 source는 E/source-dirty.patch에 보존했다. manifest에는 binary hash와 build 환경을 기록했다. source commit만으로 수정 후 binary를 특정하지 않는다.

## 실제 build

설치 경로 C:/ST/STM32CubeCLT_1.19.0. CMake 3.28.1, Ninja 1.11.1, ARM GCC 13.3.1 20240614 (GNU Tools for STM32 13.3.rel1.20240926-1715). E/toolchain.txt 참조.

각 프로젝트 디렉터리에서 실제 실행:

```powershell
cmake --preset Release
cmake --build --preset Release --parallel 4
```

대상: boot_can_custom, boot_can_isotp, boot_can_fw, boot_can_custom_f103, boot_can_isotp_f103, boot_can_fw_f103. configure는 모두 exit=0. F407 ISO-TP 헤더 수정 후 root에서 추가 실행:

```powershell
cmake --build boot_can_isotp/build/Release --parallel 4
```

F103 ISO-TP는 FLASH가 **17,224 bytes 초과**했다. 실패한 map과 원시 log를 보존했다. -Os가 이미 적용되며 Custom과 달리 CLI/printf를 사용하는 source 차이가 있다. 세부 크기 감축은 P07 선택 시 검토한다. linker 영역 확대·안전 검사 제거는 하지 않았다.

Release 이름만으로 최적화를 같다고 간주하지 않는다. compile_commands에서 F407 Custom의 사용자 코드 최종 옵션은 -Os, ISO-TP 및 application은 -O0이며 HAL driver는 -Os이다. P03에서 비교 정책을 맞추고 binary/hash를 다시 고정하기 전 본 실험을 하지 않는다. 현 binary는 P00 원형 build 근거다.

경고: F407 ISO-TP의 사용되지 않는 SendResponse, F103의 FLASH_PAGE_SIZE 재정의가 남았다. PASS는 warning-free를 의미하지 않는다. 실패한 첫 F407 ISO-TP의 implicit declaration 경고는 헤더 누락에 동반된 것이며 재빌드에서 사라졌다.

## 주소·erase·payload 점검

| 항목 | F407 양쪽 | F103 양쪽 |
| --- | --- | --- |
| bootloader 영역 | [0x08000000, 0x08010000), 64 KiB | [0x08000000, 0x08004000), 16 KiB |
| 64 KiB 실험 image | [0x08010000, 0x08020000) | [0x08004000, 0x08014000) |
| erase | flash_tbl sector 4 하나, 64 KiB | 1 KiB page 64개 (page index 16~79) |
| write | 256-byte application block, 4-byte word | 같은 block/word 단위 |
| END | image length 범위의 CRC32, polynomial 0xEDB88320 | 동일 |
| bitrate source | APB1 42 MHz / (3 × (1+11+2)) = 1 Mbit/s | APB1 36 MHz / (4 × (1+14+3)) = 500 kbit/s |

근거: 각 프로젝트 STM32F*XX_FLASH.ld, App/hw/hw_def.h, App/hw/src/flash.c, App/ap/boot_can/boot_can.c, Core/Src/main.c. 실제 외부 oscillator/보드와 bus 속도는 P03에서 확인한다.

F407 START는 양쪽 모두 FLASH_ADDR_FW=0x08010000에서 image length를 erase하며, 정상 65,536 bytes는 정확히 sector 4에 맞는다. 256 blocks는 양쪽 모두 256 bytes씩 기록한다. F407 app vector section은 ELF VMA/LMA 0x08010000, binary end=0x08018FE0, SP=0x20020000, reset=0x080131F1이다. application의 VTOR offset도 0x10000이다. 64 KiB padding 여유는 28,704 bytes이다. padding binary 생성·boot 확인은 NOT RUN이다.

**F407 원형의 경계 불일치:** hw_def의 FLASH_ADDR_END는 0x08080000(448 KiB application 범위)이나 FW_MAX_LEN은 960 KiB이고 app linker도 960 KiB이다. Flash helper는 주소 범위를 제한하지 않으며 START의 0/초과 길이는 max 길이로 바뀐다. 정상 64 KiB 분석과 별개로 큰 image·비정상 입력의 안전성을 입증한 것은 아니다. 초기 설정은 64 KiB 고정으로 제한하고 P02의 입력 검증 및 P03 hardware 진입 전에 경계 정책을 확인한다. 범위 확장 실험은 이 상태로 허용하지 않는다.

F103은 F1 HAL/CMSIS, STM32F103xB, startup_stm32f103xb.s, system_stm32f1xx.c를 실제 compile_commands에서 확인했다. 잔존 F4 파일은 compile 대상에 포함되지 않는다. F407은 F4 HAL/CMSIS·STM32F407xx·해당 startup/system을 쓴다. F103 app end=0x0800C9A8, SP=0x20005000, reset=0x08006CB5, VTOR offset=0x4000이다. F103 ISO-TP는 실행 binary가 없으므로 보드 내 비교 baseline PASS가 아니다. main staging의 0x08012000/57,336-byte 한도와 혼용하지 않는다.

## 대응 sender·CSV 관계와 후속 과제

F407 target은 boot_can_custom/boot_can_isotp, 대응 sender는 loss_test_custom.py/loss_test_isotp_raw.py와 test_runner.sh다. F103은 *_f103 target/sender 및 test_runner_f103.sh다. F407 runner는 64/128/256/512 KiB, F103은 64 KiB이며 반복 수는 사용자 입력이다. 이번 계획은 F407의 64 KiB만 선택했다.

P00에서 직접 읽은 현재 네 sender는 모두 자신의 디렉터리 fota_results.csv에 기록한다. 따라서 기존 문서의 “_f103 sender가 fota_results_f103.csv에 기록”은 현재 HEAD의 직접 출력 경로와 다르다. result/로 이동·rename한 이력이나 당시 실행 binary/dirty state는 증명되지 않았다. 기존 CSV의 조건 대응과 실제 생성 provenance를 구분한다.

| 기존 CSV | 행 수·status | 취급 |

| result/fota_results_f103.csv | 240 OK | F103 예비자료 |

E/legacy-csv-inventory.json에 hash·조건별 행 수가 있다. 기존 tracked CSV 5개와 presentation PPTX의 시작/종료 hash가 일치했다. 모든 과거 시도가 남아 있다고 주장하지 않는다.

P01/P02/P03에서 처리할 발견사항(이번에 구현하지 않음):

- P01: time.time 사용, Custom은 END ACK 뒤 종료 / ISO-TP는 0.5초 대기·JUMP 후 종료. count도 Custom은 drop 시도 포함 / ISO CF는 제외. 응답 DLC/flags/status 검증과 FC 준수 필요.
- P01: 고정 dependency BS=8, STmin=0, response timeout=100 ms. F407 sender는 BS=0/STmin=0 가정, F103은 STmin만 일부 해석하고 BS는 따르지 않는다. 256은 application bytes다.
- P02: Custom DATA 및 선택 재전송에 omission, timeout tail probe에는 미적용. ISO-TP는 CF만, 재시도 CF에도 omission. FF 포함 여부·seed·deadline·전체 실패 기록을 확정해야 한다.
- P02: ISO START/END 등의 실패 결과 누락, Custom 응답 대기/ENOBUFS의 무한 반복 가능성. 기존 sender를 바로 본 실험에 사용하지 않는다.
- P03: compiler 옵션 일치 및 Flash 범위 불일치 처리 여부를 검토하고 새 hash 고정 후 smoke.
- P07 선택 시: 현재 F103 Custom에는 5 ms busy-wait pacing이 있으나 ISO-TP는 받은 STmin에 의존한다. 과거 약 6초 CSV와 현재 sender가 같다는 근거로 쓰지 않는다. build overflow와 pacing을 함께 재검토한다.

## Hardware·제출 조건

STM32CubeProgrammer v2.20.0의 STM32_Programmer_CLI -l stlink 결과: **No ST-Link detected!** (E/build.log). 이는 현재 PC의 검출 결과이며 사용자의 장비 보유 여부를 뜻하지 않는다. 보드 접속·erase·program·FOTA를 실행하지 않았다.

BBB 주소/계정, OS·kernel, can0 실제 상태, transceiver·pin 배선·양 끝 종단, 물리 보드 모델/ID/현재 image/복구 수단은 미제공이다. SSH executable은 있지만 주소를 추정해 접속하지 않았다. P03 전에 사용자 정보와 대상별 flashing 허가가 필요하다.

[공식 홈페이지](https://www.ksma.or.kr/) 검색 색인에서 행사 안내 존재는 확인했으나 상세 페이지 직접 열기 실패로 공식 양식·deadline 독립 확인은 미완료다. [출처 기록](../../paper/references.md)에 검색/열람 범위와 논문집 목록의 예정일 불일치를 남겼다. 사용자 제공 요약문 10/16, 심사 10/30, 최종본·사전등록 11/2, 행사 11/5~7 계획을 유지한다. 저자·소속·교신저자, 트랙, 양식, 페이지 계산, 발표 형식과 마감 시각은 TODO이다.
