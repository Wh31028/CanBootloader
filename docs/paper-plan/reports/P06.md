## 실행 source 대조에서 발견한 측정 한계

P01/P05 문서의 의도한 경계는 START 직전→END ACK 직후다. 하지만 P04 실행 source는 `main()`에서 protocol 호출 직전 `begun=time.monotonic()`을 설정하고, 성공 시 `bus.send(...JUMP...)`를 호출한 뒤 `elapsed=time.monotonic()-begun`을 기록한다. protocol 함수가 반환하는 `start`는 elapsed 계산에 쓰이지 않는다. 따라서 END ACK 뒤 함수 반환·JUMP 송신 호출 처리까지 포함된다.

대조한 파일과 SHA-256:

- 보존된 `.../bbb-p04-f407-500k-20261009/fota_sender_p02-entry-v1.py`: `ba304d5f212f4bac15d7890e09800e0f2b43db3f82c4d819ecb045753fa1044e`. ISO-TP manifest fingerprint와 일치.
- 현재 `can-fota-BBB/fota_sender_p02.py`: `620ffba37e818282beeac26a1722c79c02794310575ad9c3067df17d6d0b46b1`. 보정 Custom manifest fingerprint와 일치.
- P04 root의 일반 이름 `fota_sender_p02.py` 사본은 보정 전 hash다. 보정 Custom 재현에는 위 현재 파일의 hash를 사용해야 하며 root 사본을 최신 source라고 가정하지 않는다.

이 경로에는 JUMP 전 0.5초 대기가 없고 entry 뒤 3.0초 대기는 begun 이전이다. 추가 처리 시간의 크기나 성능 순위에 미치는 영향은 분리 측정하지 않았으며, 작다고 가정하지 않았다. sender/raw/P05 출력은 그대로 두고 원고·README·handoff에 한계를 명시했다. `OK` 행 240건은 END ACK/CRC 통과와 JUMP 송신 호출 성공을 포함하며, 모두 `boot_status=JUMP_SENT_NOT_VERIFIED`다. 이로부터 240회 기동 성공을 추론하지 않는다.

## 남은 한계·검토 질문

- software omission의 DATA/CF 비대칭 및 FF/제어·응답 누락 제외, 별도 batch·다른 seed/revision, 무작위화 부재를 전문에 명시했다. 성공 CI는 일반 신뢰성 구간이 아니다.
- Custom의 `send_errors` 합계 31은 관측된 socket 송신 오류 횟수이며 transaction 실패 수가 아니다. 순수 복구 단위의 인과 효과와 전체 버스 부하는 이 자료만으로 분리하지 않는다.
- 기존 `abstract.md` 결론의 “loss 조건의 timeout 실패도 함께 발생했다”는 보정 전 기록임을 명시해야 한다. P08 정정안: “보정 전 Custom의 10건 timeout은 별도 실패 기록이며, 보정 후 유효 데이터에서는 양 방식 모두 120/120 성공했다.” 시간 단락에도 JUMP 송신 호출까지 포함되는 실제 경계 설명이 필요하다. 이번 요청이 전문만 보완하는 범위여서 요약문과 P00~P05 보고는 보존했다.
- 공식 양식/참고문헌 포함 페이지 계산/트랙, 저자 순서·소속·교신저자, 교수 검토 의견은 무엇인가? 사용자 확인 후 P08에서 반영한다.
- ISO 표준 전문은 미열람이다. Linux 문서는 개념 설명, RFC는 선택 재전송 배경, isotp-c는 구현 설정 근거로만 썼다. CAN FOTA 직접 선행연구 확충 여부를 검토할 필요가 있다.
- F103, 큰 이미지, 실제 차량, 다중 ECU, ACK loss, burst loss, 전원 차단, staging/rollback/서명은 이번 결과로 입증하지 않는다.
