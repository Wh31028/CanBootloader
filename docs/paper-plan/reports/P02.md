## 이번에 정한 규칙

- 손실은 sender가 시험을 위해 DATA frame을 일부러 보내지 않는 것이다. Custom은 256-byte DATA 묶음 안의 DATA frame만, ISO-TP는 CF(첫 frame 뒤에 이어지는 DATA frame)만 대상으로 삼는다.
- START, END, JUMP, ISO-TP의 첫 frame(FF), 그리고 ACK/NACK/FC 응답에는 손실을 넣지 않는다. 그래서 두 방식에 똑같은 번호의 frame이 빠진다고 말하지 않는다. 대신 같은 손실 확률로 각각 시험한다.
- `seed`는 난수의 시작값이다. 같은 seed와 같은 설정이면 같은 frame이 빠진다. 원래 전송과 재전송은 각각 다시 뽑으며, 실제로 빠진 위치는 JSONL 파일에 남긴다.
- 한 번의 시도는 최대 120초다. START 응답은 15초, DATA 응답은 0.15초, END 응답은 3초, ISO-TP의 FC 응답은 1초까지만 기다린다. ISO-TP DATA 묶음은 최대 4번만 시도한다. ENOBUFS(PC의 CAN 송신 대기 공간이 찬 오류)도 정해진 시간 안에 끝낸다.
- `transaction_status`는 END ACK와 CRC 확인까지의 전송 결과다. `boot_status`는 전송 뒤 application이 실제로 켜졌는지를 위한 별도 기록이다. JUMP를 보냈다는 것만으로 부팅 성공이라고 쓰지 않는다.
- 실패 사유는 socket, 송신, START, DATA, END/CRC, 전체 시간 초과, JUMP, 사용자 중단처럼 이름으로 남긴다. **ACK**는 정상 수신 응답이고, **CRC**는 파일 내용이 바뀌지 않았는지 확인하는 값이다.

## 기록과 runner

- sender는 새 `--run-dir` 안의 `raw.csv`와 `events.jsonl`에만 결과를 이어서 쓴다. 기존 `fota_results.csv`는 건드리지 않는다.
- CSV에는 시도 번호, seed, firmware hash, 전송/부팅 상태, 걸린 시간, 송신·누락·오류·재전송 횟수를 남긴다. JSONL에는 실제로 빠진 frame 위치를 남긴다. 재전송 비율의 기준은 모든 송신 시도 횟수다.
- `experiment_runner.py --config CONFIG --run-dir NEW_DIRECTORY`는 새 폴더만 받는다. 실행 전에는 계획한 모든 시도를 manifest에 쓰고, 실행 뒤에는 명령과 종료 상태를 추가한다. 프로그램이 죽어서 CSV 행이 없어도 manifest에는 그 시도가 남는다.
- config에는 firmware/bootloader hash, sender source fingerprint, firmware 경로, runner 제한 시간, 실행 순서, 각 시도의 ID·방식·손실률·seed를 넣는다. 방식에 따라 bootloader를 바꿔야 한다면 그 시점도 config에 쓴다. runner는 CAN 설정이나 bootloader flashing을 하지 않는다.
